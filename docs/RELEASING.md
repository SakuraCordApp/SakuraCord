# Releasing SakuraCord

This is the maintainer runbook for versioned SakuraCord releases. Release-note
wording belongs in the [GitHub release notes](RELEASE_NOTES_STYLE.md) and
[Discord announcement](DISCORD_RELEASE_ANNOUNCEMENTS_STYLE.md) style guides.

## Release model

A tag matching `vMAJOR.MINOR.PATCH` builds and signs the app, packages the DMG,
generates and verifies the Sparkle appcast, publishes reviewed release notes,
and posts the reviewed announcement to Discord. The downloadable archive is
named `SakuraCord.vMAJOR.MINOR.PATCH.dmg`.

Release copy is reviewed source data, not text generated by CI. Before tagging,
create and commit `Releases/vMAJOR.MINOR.PATCH.json`:

```json
{
  "schemaVersion": 1,
  "tagName": "v0.1.3",
  "githubDescription": "SakuraCord v0.1.3 adds ...\n\n## Feature area\n\n- Added ...\n\n**Full Changelog:** [v0.1.2...v0.1.3](https://github.com/SakuraCordApp/SakuraCord/compare/v0.1.2...v0.1.3)",
  "discordAnnouncement": "**Specific feature headline 🌸**\n\n**Highlights**\n- A user-facing feature"
}
```

Validate the copy before creating and pushing the tag:

```sh
node script/release_automation.mjs validate-copy \
  --input Releases/v0.1.3.json --tag v0.1.3
git add Releases/v0.1.3.json
git commit -m "Prepare v0.1.3 release copy"
git tag v0.1.3
git push origin main v0.1.3
```

The pre-push hook and release job both reject a missing, malformed, or
mismatched release-copy file.

## One-time Sparkle setup

SakuraCord pins the official Sparkle package. Generate one Ed25519 keypair on a
trusted maintainer Mac, back up the private key in an offline secret store, and
configure the repository secrets:

```sh
swift package --package-path App resolve
find App/.build/artifacts -path '*/bin/generate_keys' -type f
App/.build/artifacts/sparkle/Sparkle/bin/generate_keys
App/.build/artifacts/sparkle/Sparkle/bin/generate_keys -x sparkle-private-key

gh secret set SPARKLE_ED_PRIVATE_KEY < sparkle-private-key
gh secret set SPARKLE_ED_PUBLIC_KEY
printf '%s' 'ad-hoc-updates-are-not-notarized' | gh secret set SPARKLE_ADHOC_RELEASE_ACK
```

`SPARKLE_ED_PUBLIC_KEY` is the base64 public value printed by
`generate_keys`. Remove the exported private-key working copy only after
confirming both the offline backup and repository secrets.

## One-time Discord setup

Store the bot credential and destination IDs as repository secrets:

```sh
gh secret set DISCORD_BOT_TOKEN
printf '%s' '1528180315233714368' | gh secret set DISCORD_RELEASE_CHANNEL_ID
printf '%s' '1528177363995590795' | gh secret set DISCORD_UPDATES_ROLE_ID
```

The bot must be able to view and send in the configured channel and mention the
updates role. The bot credential does not belong in workflow logs, release
assets, or source.

## Publication and recovery

The workflow publishes Discord last. A Discord failure therefore leaves the
verified GitHub Release intact, and a retry reuses the exact committed copy.
Successful Discord delivery is checkpointed to prevent duplicate posts.

The release job stops before publication when release copy or Sparkle secrets
are invalid, the keypair does not match the packaged app, or appcast, bundle,
URL, version, or nested-signature validation fails. Local and debug packages do
not embed the production feed or public key.

Editing a published GitHub Release body refreshes the signed appcast without
changing the DMG. The release-edit workflow can also be dispatched manually
with a release tag to repair an older feed.

## Signing limitation and key safety

Current artifacts are ad-hoc signed and not notarized. Sparkle's EdDSA
signature authenticates the update archive and feed, but does not replace Apple
Developer ID signing, hardened runtime distribution, or notarization. The
GitHub DMG remains the fallback until in-place Gatekeeper behavior has been
verified from an older public build.

Treat the Sparkle private key as irreplaceable while releases remain ad-hoc
signed. Do not replace either key secret in place. Establish and verify a
Developer ID signed and notarized transition release with the old Sparkle key
before following Sparkle's key-rotation procedure. If the key is lost or
compromised before that transition, stop publishing the appcast and ship a
manual-download migration rather than weakening validation.
