# Forum channels implementation record

Observed and implemented on 22-23 July 2026. The comparison used Discord's public Channel, Thread, Permission, Message, and rate-limit documentation; Paicord revision `694761c1938b73bb60bd58942674dfe73aab1135`; Swiftcord v1 revision `14465d927ebe1ba34b3befa00f9365fad7b56eb9` (including DiscordKit revision `2d42c69cafe592300a1a9d3a307bf485294026c7`); and an authorized read-only inspection of the current official Discord client build `17ad424626550a9e7bccd11ff9ef8f83043559cb`. No authorization header, cookie, credential, or unsanitized capture was stored or replayed.

The forum UI is a dedicated primary workspace. It never loads the parent forum as a message timeline. Selecting a post opens the existing supplementary thread conversation pane, so message rendering, replies, attachments, reactions, composer behavior, and thread permissions remain shared with ordinary threads.

## Request budgets and safety

- Opening a warm forum publishes its complete cached catalogue immediately while one single-flight background `GET /channels/{forum.id}/threads/search` refreshes Older Posts. A cold forum publishes the first decoded search catalogue response immediately. Neither path waits for starter previews. Missing starter previews then cost one `post-data` mutation-shaped read per ten posts, remain single-flight per forum, and publish progressive changed batches. Valid siblings survive a malformed catalogue record. Hydrated starter and recent messages enter the same shared message cache as regular channel messages so reaction actions do not depend on opening the thread first. A preview-read failure retains the catalogue records instead of hiding otherwise valid posts. Request counts are unchanged: one first-page catalogue GET plus at most one preview POST per ten missing previews.
- One subsequent Older Posts page costs one matching thread-search GET whose offset advances by the number of server records returned. The server's `has_more` value controls continuation; active Gateway records cannot consume or displace the offset. Text search narrows cached rows immediately and, after a 300 ms debounce, costs one name-search GET for the settled query. Replaced queries cancel before transmission where possible; clearing a query restores the cached catalogue without another request.
- Opening a known forum-post link costs no navigation lookup. Opening an uncached post/thread link costs one `GET /channels/{thread.id}` through the shared scheduler, followed by the existing thread-message read after the pane opens. The resolved thread is retained in the parent forum cache.
- Creating a text-only post costs one thread POST. Attachments add one reservation POST plus one storage PUT per file before that thread POST. Creation is never automatically retried.
- Editing an attachment is local draft state and adds no request. The chosen filename is used for reservation and the final nested attachment record; spoiler state adds the existing `SPOILER_` prefix, and a nonempty description is included only in the final attachment record. File-panel URLs retain balanced security-scoped access for the lifetime of the composer draft so previews and the later upload remain valid in the sandbox, then release that access when the attachment is removed or the composer closes. Discord's public Message resource documents partial create attachments with filename and description and caps description at 1,024 characters. The user-supplied official-client screenshots on 23 July 2026 show the corresponding hover spoiler/edit/delete controls and Modify Attachment sheet.
- A tag, close/reopen, or pin change normally costs one PATCH. Discord may require a preparatory state PATCH before changing a dormant post's tags or lock state; the final lock PATCH restores the server-provided prior state. These mutations are not automatically retried.
- Deleting a post costs one bodyless channel DELETE and is never automatically retried. On success the post, its cached thread messages, and any open thread pane are removed immediately; the subsequent `THREAD_DELETE` event is idempotent reconciliation.
- Thread updates come from `THREAD_CREATE`, `THREAD_UPDATE`, `THREAD_DELETE`, and `THREAD_LIST_SYNC`. A sync replacement retains already-known locked records that are absent from the active sync payload. Message create/update dispatches refresh cached preview activity. `READY.read_state` and `MESSAGE_ACK` drive unread presentation without an extra read.
- On 24 July 2026, a startup crash report exposed a valid `READY.read_state.entries` collision between non-channel resource types sharing one resource ID. SakuraCord now retains `read_state_type`, admits only type `0` channel entries into forum unread state, and defensively resolves repeated channel entries in payload order with the newest entry winning. This is a local READY parsing correction and adds no requests or account actions.
- Every authenticated operation uses the existing central transport, rate-limit buckets, redaction, restriction circuit, and bounded retry rules. The offline fixture exercises the complete UI without Discord networking.

## Initial-load performance verification

The 23 July 2026 audit found that SakuraCord awaited the Older Posts catalogue and every sequential ten-thread `post-data` batch before assigning the first visible page. The cold-load contract benchmark gives the preview response a deterministic 550 ms delay and requires the decoded catalogue to return in under 450 ms without waiting for that request; it then verifies exactly one preview request for the missing batch. Warm navigation now republishes the complete cached catalogue, including already-paged archived records, rather than flashing only active rows and discarding the user's earlier pagination progress. Superseded forum and preview loads are cancelled across channel changes. `ForumPostsLoad`, `ForumProviderLoad`, `ForumCatalogueUpdate`, and `ForumPresentation` Points of Interest intervals cover the corresponding model stages in Instruments. The 10,000-post presentation regression remains in the app suite to guard stable identities, deterministic tie ordering, sectioning, and incremental updates under a large synthetic catalogue.

## Authenticated runtime verification

On 23 July 2026, the canonical packaged `dist/SakuraCord.app` was exercised in a user-authorized authenticated session against real forum channels. The bounded run covered immediate catalogue publication, the Active/Older boundary, pagination into posts from September-October 2025, opening an existing post in the shared thread pane, list and gallery layouts, recent-activity and creation-date ordering, tag match-some and match-all filtering, text search and clearing, default-reaction add/remove reconciliation between the card and starter message, spoiler presentation, and the filtered-empty state. A regular text channel and its existing message, media, and reaction presentation were checked before the forum run. Loading, pagination, creation, and mutation failures were exercised with deterministic offline providers rather than by deliberately disrupting the authenticated session.

One clearly labelled QA post was created in a real required-tag forum using a title, body, ordinary tag, renamed image attachment, 30-character alt text, and spoiler state. Required-tag validation kept Post disabled until a tag was selected. The resulting post opened through the existing thread conversation path and rendered the uploaded attachment. With the authenticated account's actual moderator permissions, an ordinary moderated tag was applied and removed, then close/reopen, lock/unlock, and pin/unpin were each exercised and restored. The final retained state is open, unlocked, unpinned, and carries only its original `test` tag. Permanent deletion was deliberately not automated without separate action-time confirmation.

## Deliberate scope decisions

- Forum-channel administration (creating/deleting the parent channel or editing its available-tag catalogue) remains server-settings functionality and is not exposed from the post browser. Post actions include ordinary-tag editing and close/reopen for an unlocked post owner, plus moderated-tag editing, close/reopen, lock/unlock, pin/unpin, and delete when `MANAGE_THREADS` is present. Post owners also receive the explicit delete-post action; other non-moderators do not. Archived posts remain in the existing Older Posts section rather than adding a duplicate archive-only browser.
- Paicord's archived-public route remains the reference for the public API, but the authorized current-client capture showed that Discord's desktop forum browser deliberately uses the undocumented thread-search catalogue route instead. SakuraCord follows that observed browse contract; the decoder remains isolated so a future client change fails visibly instead of producing speculative fallback traffic.
- The authenticated run was deliberately bounded to one user-visible QA post and reversible mutations on that post. It did not inspect credentials, capture or replay authorization data, send direct messages, modify another user's post, or perform unattended account actions.
